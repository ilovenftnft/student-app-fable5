# 竞品与技术路线（2026-09-01）

> 由主代理用定向搜索 + 本机实测完成（两次研究子代理均停摆后接手）。标注：**实测** = 本机验证；**官方** = 官方文档/仓库；**报道** = 新闻/社区；**判断** = 基于经验的推荐。

## 一、竞品：各解决了什么、没解决什么

| 产品 | 解决了 | 没解决 | 我们的差异化 |
|---|---|---|---|
| Anki + FSRS | 间隔复习调度最成熟；FSRS-6 已是默认可选算法 | 卡片要自己做；界面对 12 岁孩子不友好；没有"今天学了什么→该练什么"的闭环；没有家长视角 | 卡片由学校作业/考卷照片自动生成；每日闭环替代"打开 Anki 刷卡"这个需要自律的动作 |
| 小猿搜题 / 作业帮 | 拍照搜题即时给答案；海量题库；错题本 | 核心是"给答案"，与"先作答再讲解"直接冲突；广告与推荐分散注意力；数据在云端 | 不给答案只给讲解且需先作答；零推荐零广告；本地数据 |
| AI 错题本类（近两年国内产品） | 拍照识题 + 知识点标签 + 变式题 | 依赖云 API 付费；家长端多为监控式（逐题、时长）；无习惯设计 | 订阅号本地调用零成本；家长端只看"完成天数 / 薄弱点 / 一句建议"（见 02 研究第 5 条） |
| Forest / 番茄类 | 专注计时、仪式感 | 只管时间不管内容；倒计时对部分学生增焦虑 | 计时只是闭环的一部分，正计时 + 静态进度（见 05 研究） |
| Notion / Obsidian 模板 | 灵活 | 全靠自律搭建与维护；对初一学生是负担 | 零配置，打开即是今天的任务 |

## 二、Codex CLI 无头模式（主引擎）

| 项目 | 结论 | 来源 |
|---|---|---|
| 可用参数 | `codex exec -i/--image <FILE>...`、`--output-schema <FILE>`、`--json`（JSONL 事件流）、`-o/--output-last-message <FILE>`、`--sandbox read-only\|workspace-write\|danger-full-access`、`-c model_reasoning_effort=…`、`--skip-git-repo-check`、`codex exec resume <id>` | **实测**：本机 codex-cli 0.140.0 `--help`；`docs/experiments/2026-09-01-dualrun/` 单页识题 39 s 成功，与 Claude Code 结果一致 |
| 认证 | 本机及孩子电脑均为 ChatGPT 登录（`codex login status` → "Logged in using ChatGPT"） | **实测** |
| 额度 | Plus/Pro：**5 小时滚动窗口 + 周额度**两条并行，任一触顶即暂停到重置；2026-07-12 曾临时取消 5 小时限制，**2026-08-25 恢复**。具体 token/消息数 OpenAI 不公开，消耗随模型、上下文、推理档位变化；剩余额度以 Codex `/status` 或账户页为准 | 报道：[9to5mac 2026-08-24](https://9to5mac.com/2026/08/24/openai-restores-5-hour-codex-and-work-limits-for-chatgpt-plus-users/)、[TechRepublic](https://www.techrepublic.com/article/news-openai-five-hour-codex-limit-chatgpt-plus/)、[whoburnedmore 指南 2026-08-28](https://whoburnedmore.com/guides/codex-usage-limits)、[openai/codex 讨论 #2251](https://github.com/openai/codex/discussions/2251) |
| 本地脚本子进程调用是否允许 | `codex exec` 是官方文档化的"非交互模式"，就是为脚本/自动化设计的；我们调用的是 Codex 本身、用的是本机登录，不抽取 token 给第三方 SDK。**未找到明文禁止个人本地脚本用 ChatGPT 登录跑 `codex exec` 的条款**；官方对 CI 场景推荐 API key。 | 官方文档页（developers.openai.com/codex → learn.chatgpt.com/docs/non-interactive-mode，跳转未完成抓取，**待核实原文措辞**） |

**改变的设计决定**：
1. 每次调用用 `-c model_reasoning_effort=low` 做识题/标签（够用且省额度），`medium` 做讲解；周报一次 `high`。
2. 额度触顶 → 任务进队列并显示"稍后自动重试"，不报错给孩子；重置时间从 JSONL 错误事件读取。
3. 每周家长 AirDrop 考卷后集中跑一批，避开孩子晚上使用的时段。
4. 在孩子电脑上把 `codex` 二进制限制为只由 app 的 launchd 用户会话调用，是"开放通道"问题的部分技术缓解（家庭规则仍是主要手段）。

## 三、视觉模型识别中文手写作业与几何图

| 结论 | 证据 | 等级 |
|---|---|---|
| 印刷体试卷识题不是难点 | 本机实测：6 题题号/分值/册章 100% 一致 | 实测 |
| 手写数学的主要错误来源是**转录**而非评分逻辑：用 GPT-5 批改手写试卷扫描件的研究中，87% 的错误可归因于转录失败 | [Automated Grading of Handwritten Mathematics Using Vision-Capable LLMs (2026)](https://arxiv.org/html/2605.19043) | 论文 |
| 手写数学表达式识别是独立研究方向（VEHME、Uni-MuMER），通用 VLM 仍弱于专用模型 | [VEHME](https://arxiv.org/pdf/2510.22798)、[Uni-MuMER](https://arxiv.org/pdf/2505.23566) | 论文 |
| 几何图辅助线推理是 VLM 已知短板 | [GeoVLMath](https://arxiv.org/pdf/2510.11020) | 论文 |

**改变的设计决定**：
1. 流水线分两步：**先识"题"（印刷体，可靠），再识"孩子的作答"（手写，不可靠）**；作答识别结果只作参考，错题判定以"老师批改的 ✗"为准——让模型找红笔标记，而不是自己判对错。
2. 几何题一律 `needs_figure=true`，卡片保留原图裁剪，不做文字化。
3. 拍照规范写进家长页：平铺、正上方、自然光、一页一张、不要斜拍；app 自动做透视校正与裁剪后再送模型。
4. golden 评测集必须包含真实手写作业照片（≥20 张），这是印刷体真题无法替代的。

## 四、技术栈（明确推荐）

**推荐：Node 22 + TypeScript，单进程。**

| 层 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node ≥ 22（LTS） | ts-fsrs 要求 Node ≥ 20；孩子 Mac 装一次即可；launchd 常驻简单 |
| 后端 | Hono（HTTP + 静态托管）+ `better-sqlite3` | 同步 API 让 TDD 极简（无 async 噪音）；Hono 轻、类型好；单进程同时服务 API 与前端构建产物 |
| 前端 | Vite + React + TypeScript + Tailwind + shadcn/ui（Radix 无障碍组件） | 两周内做出 Things/Linear 质感最快的组合；shadcn 是源码拷贝、无运行时依赖、可深度定制成克制风格；Radix 保证键盘/焦点可达 |
| 间隔复习 | `ts-fsrs` 5.4.1（FSRS-6，零依赖，MIT） | 几百张卡片用 FSRS 还是 SM-2 差别很小（见 02 研究第 2 条），但 ts-fsrs 开箱即用、参数可后期优化，成本为零，直接用；目标记忆率设 0.85–0.9 |
| 文件夹监听 | `chokidar` 监听 `~/StudyInbox/` | AirDrop 落盘即入库 |
| 引擎调用 | `child_process.spawn('codex', [...], {stdio:['ignore','pipe','pipe']})`，按 cc-suite 骨架封装为 `engine/codex.ts`；`engine/claude.ts` 同接口可插拔 | 见计划「一·五」 |
| 测试 | Vitest（逻辑、数据层）+ Playwright（两条端到端） | Vitest 与 Vite 同栈；`better-sqlite3` 用 `:memory:` 跑集成测试 |
| 常驻 | `launchd` LaunchAgent（用户级），开机自启，崩溃自动重启 | macOS 原生，无需 pm2 |
| 数据 | 单文件 SQLite（`~/Library/Application Support/StudyApp/app.db`）+ 照片原图目录 | 备份 = 拷一个文件夹 |

来源：[ts-fsrs npm](https://www.npmjs.com/package/ts-fsrs)（5.4.1，FSRS-6）、[ts-fsrs releases](https://github.com/open-spaced-repetition/ts-fsrs/releases)；其余为**判断**。

不选的理由：Python/FastAPI（前端仍要 Node，双栈增加两周内的摩擦）；Bun（`bun:sqlite` 好但生态与 Playwright/launchd 组合成熟度略低，不值得冒险）；Electron（不需要，浏览器打开 `localhost` 即可，也避免打包工作）。

**改变的设计决定**：整个 app 一个 `npm run dev` 起来；部署到孩子电脑 = `git pull && npm ci && npm run build` + 一个 plist。
